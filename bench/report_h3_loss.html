HTTP/3 resilience: packet loss · network flaps · connection migration

Juggler v1.0.0 (QUIC :8443) · aioquic 1.3.0 клиенты через повреждённый UDP-прокси · 8 параллельных QUIC-соединений · 2026-09-26
Методика. Клиент ходит на 127.0.0.1:18443 — UDP-прокси с NAT-семантикой (пара серверных сокетов на клиента, ответы уходят с того же сокета, что запрос), который режет дейтаграммы по сценарию: случайная потеря в обе стороны, полный blackout обеих ног на T секунд, смена серверного порта (NAT rebinding → новые 4-tuple). Таймаут запроса 15s > blackout, in-flight стримы обязаны переживать обрыв средствами QUIC-recovery. Серверные свидетельства — h3_connections_total до/после.

На t=15s прокси пересаживает все 8 соединений на другой серверный порт — Juggler видит новые 4-tuple. quinn-сервер выполняет path validation (PathChallenge/PathResponse), соединения продолжают работать без единого разрыва: 26 215 запросов до и после переключения. Серверный счётчик подтверждает: новых рукопожатий после переключения ноль — это настоящая миграция, а не тихий reconnect.

Итог

Juggler QUIC-плоскость переживает потери до 10% без единого разрыва и таймаута, blackout до 5 с — без следов, 10-секундный обрыв — с одним корректным переподключением, NAT rebinding — с успешной path validation и нулём повторных рукопожатий. Худший измеренный режим (20% потерь) деградирует по throughput (78 RPS), но сохраняет все соединения. Уровень сервера: состояние возвращается к базовому (RSS 30 MB) после всех сценариев.

Оговорки: loopback + программный прокси — не реальная сеть (нет jitter, изменения MTU, reordered packets); aioquic-клиент — один стек из многих; migration проверена для NAT-rebind-сценария, но не для смены сетевого интерфейса.
