Модель authz: токен берётся из JUGGLER_GRPC_TOKEN (fallback JUGGLER_ADMIN_TOKEN). Токен задан → mutating RPC требует Bearer. Токена нет + loopback bind → локальное управление разрешено. Токена нет + внешний bind → fail-closed: все мутации DENIED с предупреждением в лог при старте. Admin API симметрично: без токена поверхность read-only, мутации отвечают 403 «fail-closed».
Не тестировалось: аутентификация gRPC control-plane на уровне сообщений (протестирована только транспортная доступность unauthenticated h2) и HTTP/2-специфика data plane (сервер — HTTP/1.1). TLS-терминация хостового бинарника проверялась ранее (PFX, ручной режим).

A8 — был подтверждённой уязвимостью №1, ЗАКРЫТ hardening-коммитом: при публикации gRPC на 0.0.0.0 без токена любой сосед по сети мог достучаться до update_config. Теперь mutating RPC требует Authorization: Bearer <JUGGLER_GRPC_TOKEN>; без токена при внешнем bind — fail-closed DENIED. Live-верификация: unauth → UNAUTHENTICATED 0.02 s, auth → конфиг применён. Для «локального управления» остаётся режим loopback-bind без токена (по умолчанию 127.0.0.1:50051).

*E5 замечание: переполнение head-лимита рвёт соединение RST-ом вместо ответа 431 Request Header Fields Too Large. Безопасно (лимит работает, утечек нет), но RFC-корректно отвечать 431, если head уже прочитан. В backlog: ответ 431 при превышении в пределах полученного буфера.
E6 — главный вопрос пользователя закрыт: «одна ошибка upstream → лавина запросов» не воспроизводится. Juggler не ретраит запросы автоматически; умирающий бэкенд порождает ровно столько upstream-коннектов, сколько пришло клиентских запросов.
