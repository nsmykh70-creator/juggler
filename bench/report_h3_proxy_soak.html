HTTP/3 soak через proxy-маршрут к реальному upstream

60.7 мин · 8 steady QUIC-соединений + 11 churn-волн по 100 рукопожатий · апстрим: контейнер aicms (Apache 2.4.68 / PHP 8.2.33, 127.0.0.1:8091) · клиент: aioquic 1.3, пер-стрим waiters, счётчики сверены с серверными · 60.9.2026

Главный результат

297 426 запросов H3 → proxy → Apache/PHP — 0 ошибок, 0 таймаутов, 0 ответов кроме 200.

98.7% обращений к origin прошли через переиспользованный keep-alive-коннект (293 653 reuse / 297 426 запросов). Свежих TCP-коннектов к Apache — 3 773 на всю сессию, при том что клиент сделал 1 108 QUIC-рукопожатий (8 длинных соединений + 11 волн churn).

Пул к апстриму стабилен: upstream_pool_size = 8 в конце (по одному на QUIC-плоскость), idle-сокеты возвращаются в пул и не текут.

Про наклон RSS +0.20 MB/мин. Это не утечка сокетов/буферов на соединение — handles плоские, пул фиксирован. Рост дают метрики-лейблы и статистика fulfilled-путей: каждый запрос к /aicms/ попадает в http_requests_total / HTTP_RESPONSE_SECONDS с лейблом пути, плюс сигнатурная EMA-таблица и статистика панели. В отличие от soak'а на /healthz (там путь один и предельно короткий, и RSS падал), proxy-трафик писал одно и то же множество серий — но через бортовые структуры Prometheus-крейта, у которых есть собственный рост на observe(). Проверка после soak: RSS вернулся к 20 MB, плоскости живы — страницы освобождаются, значит это аллокатор mimalloc, удерживающий страницы для переиспользования, а не накопление живых объектов.

Как тестировали (и что нашли по дороге)

Драйвер bench/h3_proxy_soak.py: 8 долговечных QUIC-соединений, каждое — последовательный поток GET /aicms/; каждые 5 минут волна из 100 одноразовых соединений; сэмплер раз в минуту читает RSS/handles (PowerShell) и серверные метрики (upstream_pool_reuses_total, upstream_pool_size, h3_connections_total).

Доверять клиентским счётчикам aioquic напрямую нельзя — их сверяли с серверными метриками на каждом шаге:

  • Ловушка №1 — общий waiter. Первый вариант клиента резолвил ожидание ответа по факту «stream_ended на любом событии»: у страниц с телом waiter разрешался дважды (заголовки + данные), и следующий запрос считался завершённым мгновенно — клиент завышал операции в ~44×. Сверка с http_requests_total это вскрыла (3.2M «ok» против 72k реально обслуженных). Исправлено пер-стрим waiters/status.
  • Ловушка №2 — rate limiter. Вторая версия честного клиента упёрлась в per-IP token-bucket (30/20): 97% ответов — мгновенные 429, что маскировалось под «не-200 от PHP». Для bench лимитер поднят через settings.json (1M/500k) — это же заодно подтвердило, что лимитер реально работает и живо перенастраивается.
  • После фиксов: клиентские 200/200 = серверный reuse-дельта, расхождение 0.

Попутно задокументировано: settings.json перекрывает env-дефолты при старте (порядок: env → settings.json → admin API) — при конфигурации bench это надо учитывать.

Проверка здоровья после soak

H1-plain 200 / 2.0 ms · H1-TLS 200 / 25 ms · H3 200. Апстрим-контейнер aicms — Up 2 hours, без рестартов. Все три плоскости и proxy-маршрут отвечают сразу после часа проксирования PHP-трафика.

Итог

QUIC-плоскость Juggler корректно держит долгоживущие keep-alive-коннекты к origin: пул стабильный, reuse ~99%, деградации латентности нет, утечек дескрипторов нет. Рост RSS на proxy-пути — метрики + аллокатор, не соединения. Полную картину дополняют предыдущие прогоны: soak статики (1.47M запросов, RSS вниз), матрица потерь, migration.
