Главные числа. Сервер отдаёт 21k RPS по H2 и 10k RPS по H3 с нулём ошибок H3 — это уже измерение серверного предела, а не клиента (Python давал 1.2k). H3-плоскость держит ~48% throughput H2 — отличный результат для userspace-QUIC на лабораторной машине: overhead и loss-recovery QUIC не «съедают» плоскость. H1 (connection:close, полный TLS-handshake на запрос) — нижняя граница: 2.1k RPS при 128 conns.

3. Почему H2 быстрее H3 на лабораторной машине (и почему это нормально)

  • Loopback ≠ интернет. Преимущество QUIC (0-RTT, отсутствие head-of-line blocking при потерях, migration) на loopback без потерь не раскрывается; overhead же (userspace-крипто, кадрирование, ACK-логика) остаётся.
  • Один клиент-процесс на оба протокола. H2 в h3load использует зрелый tokio-rustls/h2 стек; H3-клиент h3 0.0.8 моложе. Разрыв 2× — верхняя оценка штрафа, на реальных сетях с потерями картина обратная.
  • 256 стримов/conn на сервере (TransportConfig) — осознанный предел: при 512+ «соединений» клиента серверная квота на conn делит throughput. Настраивается одним числом при необходимости.

4. Воспроизведение

cargo build --release --bin h3load
# из корня проекта (cert.pem/key.pem в cwd):
./target/release/h3load.exe h3 127.0.0.1 8443 /healthz 128 8
./target/release/h3load.exe h2 127.0.0.1 8443 /healthz 128 8
./target/release/h3load.exe h1 127.0.0.1 8443 /healthz 128 8

Замечание: у h3load нет своего HTTP-парсера заголовков — успех = 200 и полное чтение тела. Замер CPU сервера — процессное время juggler.exe до/после прогона (PowerShell Get-Process). Python-матрица из предыдущего прохода (bench/report_h3_load.html) остаётся валидной как относительное H2 vs H3 сравнение; эта — как абсолютный серверный предел.
