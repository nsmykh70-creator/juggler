Juggler v1.0.0 — серверные пределы H1 / H2 / H3 (Rust-нагрузчик, v2)

2026-09-26 · Windows x64 release · клиент bench/h3load.rs (tokio multi-thread, quinn 0.11 + h3 0.0.8 + h2 0.4 + rustls) · keep-alive, 1 запрос in-flight на соединение (если не указано streams) · бенч-инстанс на :9085/:9443 (лимитер off, prewarm 64) · 6–8 с на точку

Что нового в v2. (1) Клиент переписан: H1 с настоящим keep-alive, конкурентные стримы для H2/H3, перцентили латентности, режим h1plain. (2) wrk-якорь для контроля клиентской честности. (3) Матрица вскрыла реальный серверный дефект производительности — stat-путь делал 2×canonicalize+read (~470 µs syscall'ов на Windows) на каждый запрос статического файла; дефект исправлен (кэш canonical-корня + один canonicalize файла), после патча статика ускорилась в 1.5–1.8×. (4) Обнаружена серверная особенность маршрутизации: root-маршрут / не отдаёт файлы второго уровня (/index.html → 404 «route not found») — документировано, обход в бенче через префикс-маршрут.

Диагноз до патча: serve_static_file на каждый запрос делал canonicalize(root) + canonicalize(path) + read(path) ≈ 470 µs файловых syscall'ов (замер: canonicalize 287 µs, read 177 µs на Windows). 12 thread-per-core шардов упирались в это раньше, чем в сеть: потолок 1.4k RPS при CPU сервера всего 7%. Патч: canonical-корень кэшируется (меняется только при reload конфига), файла — один canonicalize. Безопасность сохранена полностью: per-request каноникализация файла по-прежнему отсекает symlink-escape (юнит-тесты зелёные, 103/103).

Остаток после патча — честный файловый I/O: read() на каждый запрос принципиален для консистентности содержимого (изменения файлов видны сразу). 100 KB-файл упирается в копирование тела (~597 RPS ≈ 60 MB/s на одноядерную обработку ответа) — дальше растёт только через sendfile-стиль zero-copy, отдельная работа.

6. Методика

Бенч-инстанс: отдельный cwd (bench/srv_bench со своими settings.json/routes.json, лимитер 1M/1M ≈ off, prewarm 64), порты 9085/9443/9091 — живой инстанс на 8085/8443/9090 не затронут. Лоадер: N задач-соединений, keep-alive, латентность каждого запроса в локальный буфер (без общего лока на горячем пути), агрегация после прогона. CPU/RSS сервера — до/после каждой точки через PowerShell Get-Process. Все точки повторно проверены sanity-прогоном.

Оговорки: loopback — без потерь/jitter, QUIC на loopback не показывает преимуществ 0-RTT/migration; клиент и сервер на одной машине делят CPU (12 ядер); Windows Defender on-access скан влияет на абсолютные цифры файлового I/O, но не на относительные до/после.
