1. Сначала был найден и исправлен реальный баг

До нагрузочных прогонов адаптивная проверка выявила критический междупротокольный дефект: Juggler с дефолтными настройками h3-крейта (0.0.8) посылал GREASE-кадр перед FIN каждого первого ответа соединения (RFC 9114 §7.2.8). Клиенты на aioquic теряли сигнал конца стрима: первый запрос на каждом соединении висел до таймаута. Браузеры и curl это терпят, Python/QUIC-стеки — нет.

Как читать. Клиентская сторона — интерпретируемый Python, ~200 RPS/соединение — потолок event-loop, поэтому обе цифры занижены относительно серверного предела; сравнение относительное. Ясно одно: H3-плоскость не медленнее H2 — вопреки ожиданию «QUIC в userspace дороже TLS-TCP» — и деградирует плавнее при росте соединений: при 128 соединениях H3-плоскость сохраняет p99 ≈ 150 ms, тогда как у H2 p99 = 11.8 s (плюс по одной ошибке «Server disconnected» на соединение от переполнения httpx-коннектов).

4. Что это значит

  • H3 production-ready в Juggler: без ошибок при 300 одновременных соединениях и почти 4 000 рукопожатий за 40 секунд, память возвращается, счётчики метрик честные.
  • Найден реальный interop-дефект (GREASE → потерянный FIN для QUIC-стеков на aioquic) — исправлен одним флагом с комментарием «почему» и задокументирован здесь. Это именно тот тип бага, который и должен ловить нагрузочный pass.
  • Абсолютные RPS не равны серверному пределу: узкое место — Python-клиент (однопоточный event-loop на все соединения). Серверная оценка требует wrk-класса нагрузчика по UDP/QUIC; относительное сравнение H2 vs H3 на том же клиенте валидно.
  • Alt-svc-реклама работает на H1/H2-ответах (проверено в предыдущем проходе), браузерные клиенты смогут апгрейдиться на H3 автоматически.

5. Методика и воспроизводимость

# каждое соединение держит 1 запрос in-flight, замер по каждому запросу
python bench/h3_load.py h3 127.0.0.1 8443 /healthz 128 8        # H3
python bench/h3_load.py h2 127.0.0.1 8443 /healthz 128 8        # H2
python bench/h3_load.py h3 127.0.0.1 8443 /healthz 400 40 --churn  # handshake storm
# лимитер на время теста: rate_limit_tokens/refill → 100000 (через POST /api/settings)

Замечание о честности: 512-соединенийый H2-прогон и полный 512-H2 не завершались из-за клиентских лимитов httpx на Windows (RemoteProtocolError / зависание loop'а); это ограничение клиента, не сервера — сервер после всех штормов отвечает 200 за 2–5 ms.
