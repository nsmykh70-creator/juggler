Важно: «дрейф −54%» внутри soak — артефакт клиента, не сервера. Клиентский soak-скрипт работал в одном asyncio-цикле вместе с сэмплером и волнами; его собственный steady-throughput снижался (с 1017 до ~280 rps). Свежий отдельный клиент после soak показывает 1 738 rps на статике — выше, чем до soak (1 443) из того же прогона матрицы. Сервер ни по латентности, ни по throughput не деградировал; здоровье плоскостей подтверждено сразу после теста (h1 200/2.7ms, h2 200).

3. Хронология churn-волн

Каждая волна — 200 параллельных QUIC-хендшейков + запрос + закрытие, поверх 8 постоянных соединений. Бурсты видны в минутных дельтах (метки WAVE); суммарно 11 волн × 200 = 2 200 handshake'ов. Сервер: 0 ошибок, 0 таймаутов, handles константны, RSS после волн возвращается к базовой линии — каждая волна отработала и вычистилась полностью.

4. Методика

Драйвер: bench/h3_soak.py — два независимых воркера в одном event loop (steady + churn) и сэмплер каждую минуту: RSS/_handles через PowerShell Get-Process целевого PID, h3_connections_total из /metrics, клиентские счётчики ok/err/timeouts/handshakes. Наклоны — линейная регрессия по минутным точкам. Волновый путь верифицирован отдельным one-shot прогоном до старта (200/200 ok). Сырые данные: bench/soak_h3_results.json (60 сэмплов), лог: bench/soak_h3.log.

Оговорки: один клиентский стек (aioquic); паттерн трафика — статика, не proxy-пути; churn-волны без TLS-сертификатной ротации и без смены IP (чистые новые 4-tuple). Клиентский дрейф throughput при длинных Python-прогонах учтён и исключён из вердикта о сервере отдельным после-soak замером независимым клиентом.

Итог

Час под постоянным трафиком + 11 волн по 200 одновременных хендшейков: нулевые утечки (RSS вниз, handles константа), ноль ошибок, ноль таймаутов, латентность без деградации. HTTP/3-плоскость Juggler выдерживает часовой soak с чистойledger-сходимостью серверных и клиентских счётчиков.
