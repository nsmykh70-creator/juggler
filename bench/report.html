Takeaways

1. The historical "static is slow (154–1 046 RPS)" mystery is closed: it was the Docker Desktop vpnkit host-NAT, not the server — the same binary and files deliver 14–26k RPS inside the network. Any future host-loopback numbers must be labeled as NAT-throttled. 2. Juggler's static path is nginx-class; its proxy overhead vs direct static is within session noise at c≥1 000. 3. Remaining honest gap vs nginx stays the tail latency under 10k proxy concurrency (documented in the v1.0.0 section above), not throughput or memory.

Architecture: nginx-model sharding

First report's diagnosis: one multi-threaded work-stealing runtime accepted 10k connections through a single queue while nginx distributes accepts across kernel-scheduled workers. Juggler now mirrors that model:
  • 12 shard threads, one per core — each a current_thread Tokio runtime in a LocalSet, pinned via core_affinity. A connection lives on one core from accept to response: no cross-core migration.
  • SO_REUSEPORT listeners (one per shard): the kernel hashes connections across shards — accept balancing happens in-kernel, exactly nginx's model.
  • Deep backlogs: listen(8191) per shard + container sysctl net.core.somaxconn=8192.
  • gRPC Control Plane on shard 0, own 2-thread runtime; data-plane shards never run control traffic.

Findings

  • c=100 — Juggler dominates: +22% RPS, better at every percentile. Thread-per-core sharding without worker synchronisation is the right shape for hot low-concurrency traffic.
  • c=1 000 — near-parity: nginx −12% ahead; within this host's ±15–20% run noise (spot runs flip the ordering).
  • c=10 000 — gap closed, errors gone: −0.7% vs −13% before sharding; after pool pre-warm, warm 10k runs show 17 444 rps with 0.008% timeouts — ahead of nginx (17 147) in the same series.

Performance bugs found & fixed by benchmarking (cumulative)

#1 No upstream keep-alive — 2 467 rps, 28k errors → UpstreamPool → 20 763 rps (×8.4).
#2 Nagle enabled — 40 ms delayed-ACK plateaus → TCP_NODELAY everywhere.
#3 Stale pooled-socket race — 502 "non-HTTP response" → silent fresh-connection retry.
#4 Accept backlog 1024 — storm drops → socket2 backlog 8191 + somaxconn sysctl.
#5 glibc arena retention — 500+ MiB → global mimalloc → 267 MiB peak.
#6 Single work-stealing runtime — 10k tail (p99 2.55 s), collapse risk → sharded per-core accept + SO_REUSEPORT → gap closed.
#7 Cold upstream pool at burst start — 1.6% timeouts on opening 10k burst → pool pre-warm (256 sockets/upstream at startup + hot-reload) → 0.008% warm.
#8 Half-open probe slot could wedge — recovery flaky under concurrency → sticky probe: probe target ordered first + grant-TTL self-release. 3/3 clean integration runs.

Honest caveats

  • Plain HTTP measured (wrk cannot speak TLS) — isolates the routing/proxy engine, not the TLS path.
  • Single upstream, 21-byte responses, HTTP/1.1 only. h2 multiplexing, large bodies, multi-upstream fan-out not covered.
  • One load generator container; Docker Desktop loopback ≠ real WAN.
  • Host noise ±15–20% (WSL2 VM); treat tables as representative snapshots — rerun with python bench/run_bench.py.
  • nginx given a deliberately generous config (20k worker_connections, keepalive 512, access_log off).
